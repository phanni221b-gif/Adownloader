## 변경 사항

v0.8.4 실패 로그(F-43f41bbd)를 코드 기준으로 분석한 결과, **다운로드 동작의 결함이 아니라 진단 기록의 결함**을 확인해 바로잡았습니다. 다운로드 로직 자체는 바꾸지 않았습니다.

### 진단 용어가 기록 단계에서 되돌려지던 문제 수정

진단 이벤트는 두 단계(`MediaNetworkSession.trace()` → `FailureDiagnostics`)를 거치는데, 0.8.3/0.8.4에서 뒤 단계의 허용 목록만 고치고 **앞 단계(`trace()`)의 허용 목록은 옛 용어 그대로** 남아 있었습니다. 그래서 브라우저 네트워크(GeckoWebExecutor) 시도가 기록에서 다시 `NATIVE_INITIAL` / `requestType: UNKNOWN`로 되돌려졌고, 페이지 맥락(`content-script`) 전송은 `native`로 격하됐습니다.

- `trace()`의 transport·action·requestType 허용 목록을 현재 용어와 일치시켰습니다. 이제 브라우저 네트워크 시도는 기록에서도 `gecko` / `BROWSER_INITIAL` / `browser-fetch`로, 페이지 맥락 전송은 `content-script` / `SEGMENT_CONTENT_SCRIPT` / `content-script-fetch`로 **있는 그대로** 남습니다.
- 즉, 지난 로그에서 "gecko 시도가 native처럼 찍히던" 것은 **실제 전송이 그랬던 게 아니라 기록이 틀렸던 것**입니다. 로그상 세그먼트는 직접 연결과 브라우저 네트워크 **둘 다에서 실제로 403**을 받았습니다(서버의 접근 제한). 전송 경로 전환 자체는 의도대로 동작했습니다.

### 세그먼트 대체 경로(루트 #1)가 "왜 시도조차 안 됐는지"를 기록

루트 #1(재생 중인 탭의 페이지 맥락에서 세그먼트 가져오기)은 **그 탭이 해당 세그먼트를 성공적으로 받은 것이 관찰된 경우에만** 그 요청을 재현할 수 있습니다. 이번 로그에서는 그 관찰이 없어서(=`candidateMediaProof: not-applicable`) 루트 #1이 시도조차 되지 않았고, 보고서에는 그 이유가 드러나지 않았습니다.

- 이제 세그먼트 호스트가 모든 네트워크 경로에서 막혔고 **재생 성공 관찰도 없을 때** `SEGMENT_CONTENT_SCRIPT_UNOBSERVED`를 호스트당 한 번 기록합니다. 이는 "다운로드 대상이 실제 재생 중인 스트림으로 확인되지 않았다(또는 관찰이 만료됐다)"는 신호와, "시도했는데 막혔다"는 신호를 구분해 줍니다. 이후 로그로 **후보 불일치(앱 결함) vs 서버 차단**을 가릴 수 있습니다.

> HTTP 403은 그대로 `ACCESS_BLOCKED`로 기록되며 DRM으로 오분류하지 않습니다. DRM 해제·보호 우회·비인가 키 추출·특정 사이트 전용 예외는 구현하지 않습니다. 개인정보 보호 정책(쿠키·인증 값·응답 본문·URL 쿼리 미기록) 그대로, 기존 서명키 유지.
