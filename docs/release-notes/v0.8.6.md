## 변경 사항

v0.8.5 로그(F-faebdf4f)에서 v0.8.4의 진단 수정이 정상 동작함을 확인했습니다(브라우저 네트워크 시도가 `gecko`/`BROWSER_INITIAL`로, 루트 #1 미시도 사유가 `SEGMENT_CONTENT_SCRIPT_UNOBSERVED`로 기록됨). 이번에는 **"재생은 되는데 다운로드만 막히는" 원인을 가려낼 결정적 관찰값**을 추가했습니다. 다운로드 로직은 바꾸지 않았습니다.

### 재생 중인 플레이어의 실제 미디어 요청 결과를 관찰

지금까지 진단은 **성공한(2xx)** 미디어 응답만 기록했기 때문에, 플레이어 자신이 세그먼트 호스트에 보낸 요청이 성공했는지/실패(403)했는지가 보고서에 드러나지 않았습니다. 그래서 "서버가 플레이어까지 막는지" vs "앱이 재생 스트림과 다른 주소를 고른 건지"를 구분할 수 없었습니다.

- 확장(sniffer)이 플레이어의 미디어 요청 결과를 **호스트와 상태 코드만** 기록합니다(성공·실패 모두). **URL·헤더·쿠키·토큰은 저장하지 않습니다.** 프레임당 최대 16개로 제한됩니다.
- 실패 보고서에 `observedPlayerMediaHosts`가 추가됩니다. 각 항목은 `호스트|ok` 또는 `호스트|err` 형식(호스트 + 성공/실패)이며, 최대 12개입니다. 이것으로 다음을 **확정적으로** 가릴 수 있습니다:
  - 플레이어가 **세그먼트 호스트에서 성공(`ok`)** → 앱이 세션/맥락을 전달 못 한 문제(앱 쪽, 개선 여지).
  - 플레이어도 **그 호스트에서 실패(`err`)** → 서버가 재생 탭 외 요청을 막는 것(서버 제한, 앱 결함 아님).
  - 플레이어가 **다른 호스트에서만 성공** → 앱이 감지한 다운로드 대상이 실제 재생 스트림이 아님(후보 불일치).

> 이 변경은 **관찰·진단만** 추가하며 다운로드 전송 로직을 바꾸지 않습니다. 아직 실제 다운로드를 성공시킨 것이 아닙니다 — 다음 로그의 `observedPlayerMediaHosts`로 원인을 확정한 뒤, 그에 맞는 수정을 판단합니다. HTTP 403은 그대로 `ACCESS_BLOCKED`(DRM 아님). DRM 해제·보호 우회·비인가 키 추출·특정 사이트 전용 예외는 구현하지 않습니다. 개인정보 보호 정책(쿠키·인증 값·응답 본문·URL 미기록) 그대로, 기존 서명키 유지.
